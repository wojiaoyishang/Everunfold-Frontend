# ADR 0069：账号中心、用户授权与双向API Key接入

日期：2026-11-06（Asia/Shanghai）。状态：已按本次范围实现并验收。保留设计过程；实际接口以发布契约、[操作指南](../development/accounts.md)和[验收记录](../handoff/accounts-verification.md)为准。

## 用户确认及边界

用户要求先讨论用户管理、资料编辑、可设权限的API Key，再开始实现。其他项目只需API Key调用接口。最后明确双向通信：子项目携管理员生成的应用凭据向主项目校验Key并获得信息；管理员在主项目登记子项目URL，主项目签名回调，包括手动触发。主项目继续是Key及权限的唯一事实来源，不因此引入外部身份提供者或共享登录。

沿用基线：公开注册默认关闭，管理员创建账号；普通用户默认无发文权，编辑/直发/审核分开授权；Session与Key共用业务身份和授权，Key不突破用户当前权限。WordPress账号不迁移。用户后续授权已允许开始业务代码与页面实施，仍只在本地提交、不push。

## 页面与权限

实施选择：独立私有账号中心/account供所有登录账号编辑自身资料、密码/会话、API Key；前后台头像入口指向同一中心。后台/admin/users管理全站账号与授权，系统设置增加“API Key接入应用”。公开作者资料与私有账号信息分离，不把邮箱、会话、权限、Key、应用凭据放入公开快照。

初期保留admin/user角色，管理员是能力集合的预设，普通用户可由管理员显式授予已注册的业务能力与本人/全部资源范围。权限代码稳定、文案支持中英；前端隐藏不可用操作只是体验，后端在每条路径及目标资源检查。Key权限为用户当前权限和签发时显式权限的交集，不能借所属用户的admin角色绕过Key限制。新增能力不自动授予旧Key。

账号UUID稳定，用户名创建后不改；显示名、头像、简介、网站、界面偏好可编辑。邮箱暂不用于登录或恢复，验证/邮件渠道完成前不得标成已验证。密码使用Argon2id，改密、管理员密码重置、停用与授权变更需要持久审计；最后一个有效管理员受事务级并发保护。停用/降权同时影响HTTP、Key和已建立的协作连接，离线源文继续可导出。

## 三类凭据

| 凭据 | 用途 | 保存及限制 |
| --- | --- | --- |
| 用户API Key | 程序访问业务API，绑定用户、应用、明确权限与期限 | 高熵随机值，仅首次展示；主库保存摘要，不能读取旧明文 |
| 应用查询签名密钥 | 子项目证明自身身份后查询本应用可用Key | 与用户Key分离，只能调用应用校验能力，不能管理用户或签发Key |
| 应用回调签名密钥 | 主项目向该子项目发送真实通知 | 与查询方向独立，每个应用独立，支持轮换与撤销 |

“管理员生成签名”落实为生成/分配签名密钥，每次请求签出不同消息；不传递长期固定签名作为万能通行证。建议首版HMAC-SHA256，参考[RFC9421](https://www.rfc-editor.org/rfc/rfc9421.html)冻结消息规范，绑定方法、目标、正文摘要、应用、密钥ID、时间和nonce；算法由服务端绑定，防重放并恒定时间验签。签名验证不提供内容保密，不替代部署传输保护；当前容器HTTP测试配置不因本文自动改动。

可验证的用户Key摘要与必须用于签名的应用密钥分开保存。应用密钥只在服务端受保护存储/部署密钥引用中使用，浏览器仅在明确的一次生成操作得到需要交给应用的材料，后续管理读取只返回掩码；不进审计/任务正文/URL/普通日志。具体加密材料及协议版本随实现契约记录。

## 接入设置与接口方向

管理员登记稳定app_id、名称、启停、目标权限目录、callback_url、独立签名凭据及投递策略；主项目查询地址由部署地址和固定路径派生，界面可复制，不让子项目自报URL成为权限。地址及凭据属于私有系统设置，不能塞入现有公开site/theme投影。

- 子→主：POST /v1/auth/api-keys/introspect，子项目签名、请求体携待验Key。先认证应用，再校验Key摘要、应用归属、用户状态、当前权限、有效期和撤销状态；返回最小身份/权限/范围/版本/截止时间。不允许枚举其他应用Key。无效Key返回inactive，不披露无关用户资料。
- 主→子：POST到登记callback_url，携签名与最小事件信封。类型包括Key撤销、授权变化、账号/应用停用、测试及重新同步；只给ID、变更类型和版本，不发送原始用户Key或完整权限快照。
- 管理端：应用创建/读取/编辑/启停、凭据轮换、测试回调、重新同步、查看投递和重试，均独立真实授权/CSRF/审计。测试是无业务副作用事件；“已入队”“已接收”“已应用”分别记录，不以HTTP200假装远端缓存已更新。

回调目标只取管理员已登记地址，发送方重新检查启停/目标策略，不跟随重定向到未登记目标；私网/HTTP按当前部署许可，不为方便调试放开任意来源或所有内部服务地址。接入凭据与现有缓存节点双向Token完全分开。

## 缓存与可靠撤销

PostgreSQL仍为事实来源，Redis只承载有期限缓存/防重放/通知。用户Key到期时间与校验缓存期限分开，缓存绑定完整Key安全摘要及应用；截止时间不因命中、迟到响应或多级转存重置。首版建议普通读取最多30秒、写入每次在线确认；这是工程初值，不是已测容量或用户指定值。

撤销、用户降权/停用、应用变更与待投递记录在同一PG事务提交，再由独立Worker在事务外签名投递；稳定event_id、租约、确认和退避重试，Scheduler只唤醒/调度。重试保留event_id但生成新的请求nonce/签名。子项目验签、按事件ID幂等、保留单调权限版本后使缓存失效；迟到旧校验结果不能回填。版本检查须覆盖用户、Key及应用，不得漏掉用户降权。

Pub/Sub仅加速，断线由可靠投递和短期限兜底，依据[Redis投递语义](https://redis.io/docs/latest/develop/pubsub/#delivery-semantics)。主动推送不承诺网络分区下零延迟；权威撤销与各应用传播状态分别展示，依据[RFC7662缓存边界](https://www.rfc-editor.org/rfc/rfc7662.html#section-4)。过期且无法确认则拒绝，不能无限延长旧授权；已在执行的操作不自动回滚，延迟任务/关键步骤另需复核。

## 实施与验收顺序

1. 扩展账号模型、显式迁移、资料/密码/会话与用户管理，防越权、版本冲突及最后管理员竞争。
2. 注册能力、统一身份、用户Key和应用签名校验，业务路由及资源过滤逐项接入，发布后端契约再生成前端。
3. 应用管理、签名回调、持久投递和状态；独立子项目验签/重试/重放/乱序/迟到响应实测。
4. 账号中心/后台页及多语言，桌面/窄屏/焦点/动态与现有协作回归，真实多API进程、专用数据库与生产隔离检查。

本阶段不自动实现公开注册、邀请注册、邮箱找回、2FA或统一登录。不写假成功占位端点。实际完成项、文件/契约版本、检查与限制持续记入两仓库STATUS，最终结果以真实验收为准。

## 服务端实施记录

0019/0020落实资料、会话、用户、能力、Key、应用及回调表；accounts1.1.0、auth0.2.0、content-admin1.9.0及独立api-key-protocol1.0.0由后端发布。应用身份与audience分离；博客内置能力由代码维护，用户Key不能管理用户/应用。资料与敏感管理坚持Session，业务路由采用统一Actor、明确动作及资源范围，拒绝坏Bearer后回退Cookie；协作票据/既有WS也复核当前凭据和权限。

协议冻结为自定义EF-AUTH-HMAC-SHA256-V1，不冒称RFC9421线兼容；查询响应及回调ACK均验签并绑定原nonce。方向/代次密钥从部署主密钥派生、只首次提供，回执不持久明文；回调与业务同事务、Worker事务外HTTP、租约与迟到ACK守卫。实现和Node22子项目参考、缓存/多实例限制见[接入指南](../development/api-key-applications.md)。目前本人内容范围对混合创建者的翻译组整体拒绝，避免组级操作越权；媒体是共享库，不提供虚假的本人范围。

## 用户补充：资料与独立头像库

用户要求资料页面优化，普通用户不能直接操作完整媒体库，并确认静态JPG/PNG/WebP、单张2MiB、最长边512px、每天10次、保留20张初值，管理员可调整。个人图库按拥有关系隔离；服务端重新编码并剥离元数据，统一媒体发布与跨进程配额预留，选择头像须本人拥有且资源可用。次数按UTC日统计，接纳的持久预留计数，失败可原ID重试；删除图库项不返还当天次数，原件复用与清理由统一媒体生命周期负责。实现不授予media:read/upload能力。
