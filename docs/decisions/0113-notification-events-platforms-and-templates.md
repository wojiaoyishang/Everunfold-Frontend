# ADR0113：通知事件、平台插件与通知模板

日期：2026-11-11。状态：第一版已实施。

## 背景

现有邮件功能只覆盖 SMTP 配置和主动测试发送，业务提醒尚未接通。未来通知渠道可能包括站内、邮件、短信、Webhook 和外部消息总线，不能把“邮件提醒”做成业务事件上的单一布尔开关。

## 决定

1. 业务模块只发布稳定通知事件，不直接读取收件人或发送邮件。
2. 核心持久化事件、路由、模板、接收目标、投递记录和站内 Inbox；外部网络副作用由 Worker 执行。
3. 平台通过后端插件能力注册。内置平台为 `in-app` 和 `email`，后续短信/消息总线平台实现同一接口。
4. 平台只接收核心解析后的投递对象，不自行决定接收人、权限或通知偏好。
5. 通知模板统称“通知模板”，按事件、平台、语言保存变体；模板不存在时使用代码内置安全默认文案。
6. 模板采用受限插值，不执行 JavaScript、Jinja 或任意模板代码。缺省变量和缺失平台变体不能抛异常。
7. 初始事件为评论待审核；后续已增加定时发布成功、定时发布失败和节点最终同步失败。业务事务提交事件和去重键，Worker 生成站内与可选邮件投递。
8. 站内通知是核心能力；邮件复用当前 SMTP 私有配置，但 SMTP 结果未知时不自动重复发送。
9. 第一版邮件模板只编辑主题与纯文本正文。该边界已由 [ADR0117](0117-html-notification-templates.md) 替代：邮件现支持经过清洗的可选 HTML，发送时仍保留纯文本回退。
10. 第一版外部接收目标不建立手机号 Endpoint 表。邮件目标只取账号资料中的邮箱，未填写时投递为 `suppressed`。账号邮箱验证由ADR0115单独交付；通知模块只读取当前验证状态，不能自行把任意邮箱标记为已验证。

## 数据边界

- `notification_events` 保存不可变事件与受限模板数据。
- `notification_routes` 保存事件、接收人策略、平台和模板键。
- `notification_templates` 保存事件/平台/语言的启用状态、受限文本和修订。
- `notification_deliveries` 保存逐接收人、逐平台投递状态、幂等键、租约与重试。
- `notification_inbox` 保存站内消息和读取状态。

外部平台所需的手机号、聊天账号或 Webhook 目标由平台插件按稳定用户 ID 自行管理；核心第一版没有通用的 `notification_endpoints` 表，也不把平台凭据复制进事件或投递载荷。

## 接收人与权限

路由接收人使用 `user`、`role` 或 `permission` 策略。后台配置需要 `settings:write`，站内 Inbox 只读取当前账号自己的记录。业务事件不能通过请求参数指定任意收件人或平台 URL。

## 失败语义

- 平台可声明 `idempotent`、`retry-safe` 或 `unknown-no-retry`。
- 明确失败按指数退避重试，并设置最大次数。
- 结果未知时不自动重发，保留为 `unknown` 供人工判断。
- 站内通知和外部投递独立；邮件失败不影响站内消息。
- 平台停用或配置缺失时投递标记为 `suppressed`，不阻断业务事务。

## 事件扩展（2026-11-11）

- `content.scheduled_published` 与 `content.schedule_failed` 由排期发布结果产生，去重键包含草稿 ID、排期运行 ID 和事件类型。成功、失败、审计及内容状态在同一事务提交。
- `settings.delivery_failed` 只在设置/内容快照投递达到最大尝试次数后产生一次；不把每次网络重试都当作业务事件。事件去重键使用单条同步投递记录 ID。
- 业务模块只发布事实，不在发布事务中读取接收人或执行 SMTP。是否邮件提醒继续由后台路由决定。
- 可以按需增加失败优先级事件；成功确认、摘要和批量告警必须允许关闭，不应强制全员订阅。

## 后续

- 插件平台配置界面、短信/Webhook 示例和消息总线 Bridge。
- 用户通知偏好、免打扰、摘要和退信抑制。
- 更多事件：评论回复、运行任务连续失败、待审核积压和译文待核对摘要。
- 账号注册、找回密码和邮箱验证等账号操作暂不并入本轮业务事件总线。
