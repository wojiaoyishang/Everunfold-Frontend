# Everunfold — 博客重构设计基线（v2.11）

> 导出说明：Everunfold 为项目名称；正式代码仓库为 `everunfold-frontend`、`everunfold-backend`。既有域名 `lovepikachu.top` 和 Redis 配置中的项目主键 `lovepikachu` 不随命名变更。以下保留原文档的技术约定。

截至 2026 年 10 月 29 日，设计基线 v2.11。

重构目标是一个单站点、多用户、前后端分离的博客与轻量 CMS：FastAPI 管理业务与数据，Next.js 负责资源和页面渲染；家庭服务器提供完整服务，云端保留公开内容的只读副本。当前处于规划阶段，以下约定不代表功能已经实现。

本文集中维护已确认需求、由这些需求推导出的实现约束和待决定事项。示例表名、字段名、接口路径及代码签名用于说明语义，尚不构成冻结的数据库 DDL 或完整 API 契约。后续决定继续更新本页，不另起多份互相矛盾的主文档。

# 已确认的项目范围

- 单站点、多用户，不做多租户站群。

- 从 WordPress 迁移文章、普通页面、媒体，以及保留的历史评论；不迁移原用户账户。

- 旧主题作为视觉与交互参考，不直接运行原 WordPress 主题或 PHP 插件。

- ChatWithMe 等其他应用保持独立，不将其内部业务并入博客核心。

- 普通用户默认没有发文权限。支持游客评论、邮箱验证能力、可选 2FA，预留第三方登录；邀请注册暂不实现。

- 公开内容需要适配 SEO、多语言 URL、缓存和离线只读访问。

- 不做后台任意 JavaScript 下发，不做通用可视化页面搭建器。主题、自定义页面和可执行交互组件由可信前端代码定义。

# 技术栈与职责边界

| 部分 | 已确认职责 |
| --- | --- |
| PostgreSQL | 主业务数据库，保存内容、账户、配置及其他业务数据 |
| SQLAlchemy | 数据库交互和模型层，保留今后迁移数据库的空间 |
| FastAPI | 身份认证、权限判断、业务 API、数据读写、内部数据读取接口及缓存更新触发 |
| Next.js | 主题、页面结构、Markdown 和 HTML 渲染、可信交互组件、公开数据与渲染缓存 |
| 浏览器 | 异步获取登录状态与私有数据，直接请求 FastAPI 执行业务交互 |
| Celery Worker | 后台任务，如搜索文档更新、WebP 生成和同步；不负责文章 HTML 渲染 |
| 自研 Scheduler | 独立单进程运行的第一方轻量调度程序，与 FastAPI、Worker 共用后端代码体系与基础包，但不共享进程；仅负责计算计划执行时间和向 Worker 队列投递到期任务，是定时任务的唯一调度投递者，不加载或执行具体业务 |
| Redis | 已讨论采用的任务 Broker 与跨进程协作基础；具体缓存和 Session 存储职责另行定稿 |

运行模型支持 FastAPI/Uvicorn 多进程、Celery Worker 多进程。任务计划与执行记录需要持久化，不能只存在进程内。

SQLAlchemy 有利于隔离数据库差异，但 PostgreSQL 专有搜索、索引、类型与锁仍可能需要适配，不能把未来迁移承诺为“只改连接字符串”。

# 用户通信与内部通信

两类通信必须独立设计，Next.js 不是浏览器业务 API 的必经中转层。

| 链路 | 用途 |
| --- | --- |
| 浏览器 → Next.js | 获取公开页面、主题资源、已缓存内容和资源渲染结果 |
| 浏览器 → FastAPI | 登录、用户状态、权限相关数据、评论、表单、后台管理等业务操作 |
| FastAPI / Celery Worker → Next.js | 向已配置的前端接收端清理、刷新、预载缓存；由 Worker 投递、监控与重试 |
| Next.js → FastAPI | 通过唯一配置的后端数据源接口补齐缺失的公开资源，或执行后端触发的刷新操作 |

Next.js 正常渲染公开页面优先使用本地缓存，不因每次访问而固定回源。用户的手动业务请求属于浏览器 → FastAPI，不计为 Next.js 的服务间调用。

**Q18 已确认的 API 入口与路径：**生产浏览器业务请求直接访问配置项 `BACKEND_BASE_URL` 指定的独立后端地址；文档不指定固定生产域名或隐含域名默认值，具体地址仅在配置示例及部署配置中填写。FastAPI 公开业务路由统一注册为 `/v1/*`，生产完整地址由 `BACKEND_BASE_URL` 与 `/v1/*` 连接得到，不注册 `/api/v1/*` 作为后端业务路径。开发时可使用同源反向代理：浏览器访问 `/api/v1/*`，代理剥离最前面的 `/api` 后转发至 `BACKEND_BASE_URL` 下的 `/v1/*`。`/api` 是可选开发代理入口，不属于后端基地址或正式 API 契约。内部服务接口与 WebSocket 路径独立定义，不因地址配置自动改名或暴露。

服务地址统一由以下配置项提供，前后端及服务间认证信息按用途隔离：

- `BACKEND_BASE_URL`：后端服务的绝对 HTTP/HTTPS 基地址，不含凭据、业务版本 `/v1` 或开发代理入口 `/api`。生产浏览器直接使用该地址，Next.js 服务端与开发代理默认也连接它。启用开发代理时，浏览器改用相对入口 `/api`，代理上游仍读取 `BACKEND_BASE_URL`，不把这个配置项改为相对地址。业务端点始终写 `/v1/...`，由统一客户端连接地址与路径。

- Next.js 仅服务端的后端连接及内部请求校验配置统一放入 `backend`：`base_url` 为服务端连接地址，`allowed_peer_ips` 为接收 FastAPI/Celery Worker 请求时的实际 socket 来源允许列表，`nextjs_to_fastapi_token_env` 与 `fastapi_to_nextjs_token_env` 分别为两个方向的 Token 引用。`base_url` 省略时从部署配置的公开 `BACKEND_BASE_URL` 装配；显式填写时只覆盖服务端连接，可使用受保护的内部绝对地址，不替代浏览器的公开后端地址。整个 `backend` 对象、内部地址覆盖项和凭据不得暴露给浏览器；前端不再另设 `internal_auth` 配置，`FRONTEND_NODE_ID` 仍是根级的本机身份标识。

- `frontends`：以稳定节点 ID 为键的前端配置映射，例如 `[frontends.web-main]`、`[frontends.web-mirror]`；每个节点直接配置 `base_url`、是否参与后端定向投递的 `enabled`，以及 `nextjs_to_fastapi_token_env`、`fastapi_to_nextjs_token_env` 两个方向的密钥引用。前者供后端校验该 Next.js 节点来访，后者供后端调用该节点时使用。地址与双向凭据归属于同一节点，不使用无身份的地址列表或分离的后端节点凭据表。前端 `FRONTEND_NODE_ID` 与该键一致；更换域名不改变节点身份，回执、重试和幂等仍按节点 ID 记录。示例 ID 不隐含自动主备切换规则，地址配置不授予 CORS、CSRF 或内部接口权限。

“可配置”已确认；通过运行时公开配置接口或初始化注入实现，是当前实现建议，不要求固定为 `/runtime-config`。公开配置不能包含服务凭据。

# 后端模块入口与扩展注册

FastAPI 模块唯一的启动装配入口为 `router_init(ctx)`，不增加 `settings_init` 等并行初始化入口。Worker 的 `tasks.py` 属于可独立导入的任务函数声明，不是 FastAPI 模块初始化的第二入口。

- 路由、处理函数及任务声明可以位于模块外层，不必全部写在初始化函数内部。

- 初始化入口返回字典，其中包含 `router` 对象和模块元信息，便于发现、诊断与维护。

- FastAPI 在 `router_init(ctx)` 中注册服务、设置、组件、任务管理元信息，以及仅面向 FastAPI 进程间的广播订阅；具体 Worker 任务执行函数由独立任务模块加载。

- 无需异步操作时可用普通函数；需要异步操作时允许 `async def router_init(ctx)`。

- 设置与界面同时保留简单声明式表单、可信自定义组件两种方式。

- 注册信息可以携带模块 ID、版本、依赖、权限等元信息；具体 Manifest 字段在接口设计阶段确定。

入口示意，不是最终 SDK：

```python
router = APIRouter()

@router.get("/example")
async def example():
    ...

async def router_init(ctx):
    # 通过 ctx 注册或取得需要的能力
    return {
        "router": router,
        "id": "example",
        "version": "1.0.0",
    }
```

模块初始化上下文是应用生命周期对象，不用于保存某次请求的当前用户或语言。进程内初始化、连接创建和全站只执行一次的迁移任务应分开处理，不能因多个 Worker 启动而重复修改全局数据。

- 模块允许通过 `ctx.services.register("<module>.<service>", factory=...)` 声明供其他 FastAPI 模块使用的进程内服务；服务名带命名空间，实例只存在于当前 FastAPI 进程，生命周期与释放方式在服务接口规范中明确，不附加 Worker/Beat 角色实例化语义。

- 模块支持依赖其他模块。依赖信息在静态 `manifest` 中预先声明，由加载器完成存在性、版本兼容性与依赖顺序检查，再调用 `router_init(ctx)`；不另设初始化入口。

- `ctx` 只在 `router_init(ctx)` 中使用，不传入普通路由、任务函数或请求。运行时能力由独立服务接口或 FastAPI 依赖注入访问；用户身份、数据库会话等请求级资源不保存于全局 `ctx`。

模块不采用热安装或热卸载。新增、修改、移除扩展代码通过部署并重启相关服务生效；即使移除插件代码，原有业务数据也必须保留，框架默认不提供插件数据清理功能。

- **Q56 插件数据库迁移：**每个插件自行声明、实现并维护自己的数据库迁移逻辑和版本，管理员在安装或升级部署时手动参与、确认并执行；不由 FastAPI、Worker 或 Scheduler 启动时自动执行插件迁移。核心保留迁移版本记录与安全调用/错误报告的扩展接口。插件即使被移除，其历史数据默认仍保留；插件的独立安装指部署环节，不意味着运行时热安装。

- **Q64 核心数据库迁移：**与插件迁移一样，核心 schema 变更通过显式部署迁移命令执行，管理员在部署流程中手动参与；迁移成功后再启动或切换 FastAPI、Celery Worker 与 Scheduler。三个运行进程均不在启动时自行发起核心或插件结构迁移。

# 任务调度与广播

广播只作为 FastAPI 服务进程之间的轻量事件机制，分为**同一进程内**和**跨 FastAPI 进程**两种传播范围；不能用广播承担全局只执行一次的业务工作。Scheduler 唤醒与 Celery 任务投递各自拥有独立接口和 Redis 通道，不混入广播 API。

- 仅 FastAPI 相关进程初始化各自的广播监听器，并订阅独立命名空间的 Redis Pub/Sub 通道。Celery Worker 与独立 Scheduler 不订阅 FastAPI 广播、不调用 FastAPI 进程内注册服务。进程中的监听函数注册不共享实例；跨进程的只有事件消息。

- FastAPI 通过任务队列投递普通任务，Worker 负责执行；调度器按持久计划向 Worker 队列投递到期任务，不采用向所有进程广播执行命令的模式。

- **Celery 任务通道（Q70）：**业务任务直接经 Celery 原生的 `delay()`、`apply_async()` 或按名称 `send_task()` 投递；可以封装参数校验、任务展示、统一日志等薄层接口，但不重新设计消息广播式任务协议。Worker 按自身注册表和 `tasks.py` 执行任务，不通过 HTTP 访问 FastAPI 服务注册器，也不运行 FastAPI 的 `router_init(ctx)`。FastAPI 的任务声明供后台发现、权限和调度元信息使用，不等同于 Worker 的运行时服务注册。

- **调度器通道（Q39）：**自研轻量 Scheduler，不再以 Celery Beat 适配器作为首版实现。它是博客后端的第一方基础服务，与 FastAPI 共用必要的配置、持久化模型及日志规范，并以独立单进程运行，不调用 FastAPI 的进程内服务。Scheduler 从 PostgreSQL 获取权威计划，到期时作为唯一的周期性计划任务投递者向 Worker 的具名任务队列投递；无论 FastAPI 启动多少服务进程，都不由 FastAPI 进程扫描并重复投递定时计划。Scheduler 不加载业务任务实现、不直接处理业务；Worker 独立加载并执行具体任务。**计划热更新（Q43）：**FastAPI 在 PostgreSQL 提交计划修改后，向 Scheduler 发出仅用于唤醒的定向通知，不携带完整任务配置；Scheduler 收到后校对配置版本并从数据库重载。同时 Scheduler 定期读取数据库的计划版本，即使通知丢失也能发现变更。此通道不属于 FastAPI 进程间广播。**运行方式已确认（Q40）：**Scheduler 是与 FastAPI、Worker 分开的独立单进程程序；三者共用后端代码体系而非运行进程。定向唤醒通过 Redis 的独立通知通道发送，建议使用 `scheduler.notify_plan_changed(plan_id, version)` 等专用接口；这不是 FastAPI 事件广播，也不是 Celery 任务。通知只表示“需要重载”，不传完整执行配置，任务元数据边界待进一步确定。

- **FastAPI 广播通道（Q70）：**`emit(event, payload, scope="local"|"process")` 明确控制事件范围：`local` 只在发起进程分发，`process` 先本地分发、再经 Redis Pub/Sub 传播到其他 FastAPI 进程（Q71 已确定：本地仅分发一次，Redis 发送者回环必须跳过）。`on(event, handler, at="local"|"process"|"all")` 按**事件来源**过滤：`local` 只接收同进程产生的事件；`process` 只接收其他进程产生的事件；`all` 接收两者。Redis Pub/Sub 为不持久化的尽力通知，订阅者离线可漏收，因此重要数据变更仍依赖 PostgreSQL 持久版本、Outbox、定向投递与 Celery Worker。

## Q70～Q71 FastAPI 广播协议（已确认）

- FastAPI 每个进程分别在 `router_init(ctx)` 或对应模块初始化函数中注册自己的回调。运行时可直接通过统一的 `broadcast.emit(...)` 调用，不要求普通路由函数持有初始化 `ctx`。

- **确定的分发表（Q71 选择 A）：** `at` 表示事件的实际来源，而不是 Redis 通道名。`emit(local)` 只触发发起进程的 `at=local/all`；`emit(process)` 触发发起进程的 `at=local/all`，同时触发其他各 FastAPI 进程的 `at=process/all`。发起者进程必须忽略自己从 Redis 收到的回环消息，避免重复触发。

| 发起方式与接收位置 | `at="local"` | `at="process"` | `at="all"` |
| --- | --- | --- | --- |
| `emit(local)`：发起进程 | 触发 | 不触发 | 触发 |
| `emit(local)`：其他进程 | 不触发 | 不触发 | 不触发 |
| `emit(process)`：发起进程 | 触发 | 不触发 | 触发 |
| `emit(process)`：其他进程 | 不触发 | 触发 | 触发 |

- 跨进程消息建议含 `event_id`、`origin_instance_id`、`event_name`、`schema_version`、`payload`；每个 FastAPI 进程启动生成不同 `origin_instance_id`，接收端跳过自身回环，监听器重复注册需在本进程内去重。

- **跨进程广播不是全局单次执行：**假设 4 个 FastAPI 进程，一个 `scope=process` 事件可能触发 4 个 `at=all` 回调，这是期望的状态同步效果，不适合通过回调发送一次邮件、清 CDN 或投递一次具名任务。此类一次性业务副作用由原业务操作投递 Celery，并按业务 ID 幂等处理。

- **独立 Scheduler 通道：**`scheduler.notify_plan_changed(...)` 仅向独立单进程 Scheduler 的 Redis 通道发送唤醒信号，后者从 PostgreSQL 校对计划版本。**独立任务通道：**使用 Celery 原生方法及薄封装投递 Worker，不走广播。

- 启动任务、内部调度和任务发送不统一包装成全局广播，避免多进程重复执行和广播放大。

- 后台可以发现并手动执行代码声明允许手动运行的任务，也可为允许调度的任务建立计划。

- 任务执行权限、参数验证、计划、运行记录和日志需要统一管理。

- **任务运行时展示：**Celery Worker 的任务函数可手动调用类似 `create_progress(...)`、`update(...)`、`create_component(...)` 的接口注册进度和自定义结果组件，最新状态写入自有命名空间的 Redis 键；仅在浏览器打开任务页面时由浏览器经 FastAPI 持续查询，未打开页面时不收集进度变化时间序列。Next.js 根据可信代码内定义的组件类型渲染，FastAPI 不下发可执行 JavaScript。

- **任务终态持久化（Q45）：**任务执行结束时将最终状态与结果写回 PostgreSQL，运行期 Redis 快照可以自然过期或手动清理；查询已经完成的任务时，FastAPI 直接返回数据库中保存的结果，不依赖 Redis。**组件持久化规则（Q46）：**默认将已注册展示组件的最终结构与状态一并写入 PostgreSQL，之后可以从数据库重建任务结果页面；组件允许显式设置 `persist=False`，从最终快照排除自身，避免保留不需要的临时状态。异常中断的最终状态认定仍待细化。

- 任务重叠时默认跳过，同时允许根据场景配置排队、并发或其他可信策略；具体策略集合不在此锁死。

- 因离线或停机错过的任务默认跳过，后台日志页面警告，由管理员决定是否补跑。未来可增加邮件提醒。

- **定时任务投递可靠性（Q42）：**每次计划触发使用唯一的 `schedule_id + planned_run_at` 作为执行标识，Scheduler 在同一 PostgreSQL 事务中记录该次执行、待投递 Outbox 事件与下次触发时间，再从 Outbox 向任务 Broker 投递，失败可补投。Worker 对执行标识进行幂等检查，具体业务处理也应保证必要的幂等性；该机制降低重复与遗漏风险，不承诺跨数据库、消息队列和外部副作用的绝对一次执行。此处的发送中故障恢复与“停机期间错过计划默认跳过”是不同规则。

- 重要业务数据同步不能只依赖无持久化通知。缓存变更与业务事务一起记录为待投递事件，Celery Worker 按前端接收端逐个投递，追踪每个节点的确认、错误、重试和实际执行阶段。重复事件必须幂等，单个节点失败不能让其他节点的投递失效。

- **Q58 系统事件与通知：**FastAPI 业务操作产生可识别的事件，并通过具名 Celery 任务异步执行邮件、审核提醒、管理员告警等处理；事件源不在 HTTP 请求中同步承担发送耗时操作。重要通知可利用现有持久事件/Outbox 与重试约定保证可追踪投递，具体通知模板、接收者规则和通道类型由相应模块配置。

注册可采用装饰器等代码声明方式，但装饰器名字、参数签名和限流语法尚未冻结。任务投递不因使用注册器而变成广播。

# 内容对象与渲染

文章与普通页面共用内容对象，通过类型和布局元信息区分。

- 后台可以创建 `article` 和普通 `page`。

- **Q75 完整多块内容已确认：**文章/页面正文的 `content` 统一为有序字典列表，可包含任意数量的 Markdown 与 HTML 块，允许同篇混合、插入、删除和调整顺序。默认创建只放一个 Markdown 块，编辑器不强迫每段文字拆块；插件可通过受信任的代码声明扩展类型，具体注册与安全规则由前端 SDK 细化。

- **Q81 数据库存储已确认 A：**文章/页面的正式正文、已提交修订快照以及公开数据快照统一以 PostgreSQL `JSONB` 有序字典列表存储，与前端 API 的 `content: [{id,type,content}, ...]` 结构保持一致，允许 Markdown/HTML/可信插件块混合。每块 ID 稳定；首版不强制将每个内容块规范化成独立数据库表。Yjs 二进制协同更新日志、检查点与正式 JSONB 内容快照分开管理。

- **Q73～Q75 最终数据边界：**前端 API 的 `content` 必须是列表，每块至少有稳定 `id`、`type`（默认 `markdown` / `html`）和源文本 `content`。同一篇可以混合多个不同类型的块；**实时协同与提交审核均以整篇文章/页面草稿为单位**，不为每个块单独建独立发布和审核流程。短代码允许内嵌在 MD/HTML 块文本中，不强制作为独立类型。Q81 已确认正式快照直接使用 PostgreSQL JSONB 与接口同构；必要的索引和数据库约束在 Schema 阶段确定。

- 最终展示为 HTML，由 Next.js 渲染；不安排 Celery Worker 渲染文章正文。

- **Q79 HTML 安全已确认 A：**Markdown/HTML 正文必须经过统一的可信渲染与安全过滤策略，允许经校验的 HTML 元素、属性和样式，禁止从内容数据库执行任意 JavaScript；需要交互时使用可信前端组件/插件。管理端实时预览也应用相同安全边界。WordPress 迁移应报告被过滤或无法兼容的旧标签/样式，尽量保留安全的视觉效果。

- 支持预设布局，页面元信息保存在数据库。

- 自定义页面由 Next.js 中的可信代码渲染，数据库保存页面标题、路径、组件标识和相关元信息。

- 内容历史版本与恢复直接纳入设计，不留到以后才补。

- **Q66 历史修订存储：**正式创建的修订保留整篇内容及对应元信息的完整快照，不以差异链作为唯一恢复依据；WebSocket 期间的每次细微编辑不需要都生成永久 Revision。完整快照建议包含有序内容列表及各块原始正文、类型与稳定 ID、标题、摘要、SEO、拟发布 URL 及分类/标签关联，以准确还原当时版本。

- **Q62 软删除与保留：**文章、页面和媒体默认采用可恢复的软删除，不立即删除数据库记录和媒体物理文件。删除或撤回公开资源须使公开路由与缓存不再展示其正文；媒体清理前检查当前内容、历史修订及其他引用，物理文件的最终清理由具有权限的管理员明确发起。软删除与公开 URL 返回 404/410 等具体状态码在 API 契约阶段确定。

- **Q51 多人实时协同编辑：**具有相应权限的多个用户可以同时编辑同一篇文章/页面的共享草稿。编辑区域必须实时显示所有当前在线协作者的光标、选区及对应身份标识（例如名称和颜色）；同时可展示在线人员列表。Yjs CRDT 用于整篇正文的实时协同；人员在线状态/光标属于临时 Awareness，不纳入永久正文及正式修订。断线重连补齐、数据库落盘节奏和审核冻结边界仍待细化。

- **Q53、Q73、Q75 协同粒度：**一篇文章或页面的共享工作草稿对应一个 Yjs `Y.Doc` 和一个 WebSocket 文档房间，所有协作者在其中编辑整个有序块列表。建议 Yjs 内使用 `Y.Array` 维护块 ID 顺序、`Y.Map` 保存稳定 ID 对应的块属性、每个文本块的 `Y.Text` 保存正文；它们属于**同一个协同文档**，不是每个块独立的协同业务服务。FastAPI 负责 WS 鉴权、进程内房间连接、中继和持久化，Redis 独立通道处理跨 FastAPI Worker 同步；Awareness 汇总所有在线编辑者的光标、选区与身份。

- **Q77 协同元信息已确认 A：**同一文章草稿的标题、摘要、分类、标签、SEO 等编辑字段纳入整篇 Yjs 协同文档，使所有在线协作者看到实时变化；正式发布状态、审核决定、访问策略和权限变更仍由独立 FastAPI 业务 API 处理。URL 冲突、分类/标签有效性等必须在服务端入库、审核或发布前验证，Yjs 合并不能绕过业务约束。

- **Q78 断线编辑已确认 A：**网络中断时浏览器可继续编辑，并将尚未获得 PostgreSQL 持久化 ACK 的 Yjs 更新保留在本地 IndexedDB；恢复后先重新鉴权，再利用 State Vector 补齐/合并并重试未确认更新。离线内容明确标记为“仅保存在本机”，不能误显示为“服务器已保存”；若权限撤销则拒绝上传，并允许用户导出未同步的个人草稿。

- **Q72 协同算法已确认 A：**以 Yjs 的 CRDT 机制为基础，不自行实现 OT/CRDT 算法。Next.js 管理端的浏览器编辑器持有协同状态；FastAPI 检查 WebSocket 身份和内容编辑权限、按文章草稿隔离房间、接收与传播 Yjs 二进制更新，并负责持久化；多个 FastAPI 进程通过 Redis 独立协同通道交换更新。该通道与 Q70 的普通业务广播、Scheduler 唤醒、Celery 任务严格隔离。仍需冻结 Redis 更新包、连接/重连同步及检查点清理策略；Q76 已确定 PostgreSQL 提交成功后才发送持久化确认，临时 Pub/Sub 不能作为唯一数据副本。

## Q75 WebSocket 跨 FastAPI Worker 转发机制（详细协议待审）

- FastAPI Worker 指 Uvicorn/FastAPI 的独立服务进程，不是 Celery Worker。每个 FastAPI 进程只维护自己接入的 WebSocket 连接，例如 `room_id -> local WebSocket connections`，不能访问其他进程的 Python 内存。

- **建议转发路径：**某个 Worker 收到经过授权的 Yjs 更新，并按 Q76 提交 PostgreSQL 后，向本进程同文章的其他 WS 连接分发，并在独立的 Redis 协同频道发布一次；其他 FastAPI Worker 订阅到消息后，仅转发给各自持有的该文章本地连接。没有该房间连接的进程不必创建文档实例。频道通过统一 Redis 命名空间入口派生，如默认配置下的 `lovepikachu:collab:{draft_id}:updates`，不通过 Q70 的普通 `broadcast.emit()` 触发业务监听器。

- 消息元数据建议至少包含 `document_id`、`update_id`、`origin_instance_id`、`protocol_version` 和 Yjs 二进制 `update`。发布进程收到自身 Redis 回环时跳过；接收端可按更新 ID 去重。Yjs 更新可幂等合并，但持久化记录仍应拥有独立的重复检测策略。

- 在线人数、名字、颜色、光标及选区使用独立的 Awareness 消息传播到其他 Worker 的房间连接；这是会话临时状态，不写入正式文章 Revision。WS 断开、心跳超时或进程失效时移除陈旧状态。

- **可靠性边界：**Redis Pub/Sub 是尽力广播，离线进程会漏消息。因此 Yjs 更新需另有持久记录/检查点；连接建立、重连及必要的周期校对须通过 Yjs State Vector 与持久状态补齐遗漏，而不是假设每条 Redis 通知必达。正式 Revision 仍仅由既定审核/发布流程冻结。Q76 已确认由 PostgreSQL 持久化决定 WS 的持久化 ACK；重连后以状态向量从权威持久状态恢复。

- 权限撤销后相关 WS 连接需要及时断开或禁止继续写入；跨 Worker 传播权限版本变化可采用独立控制通知，但最终写入必须重新检查权威权限状态。

## Q76 协同编辑持久化与确认时序（已确认 A）

- **权威存储：**FastAPI 接受并验证合法 Yjs 更新后，将其按草稿文档 ID 和唯一更新 ID 写入 PostgreSQL 的协同更新日志，提交成功后才向发送方发出**持久化 ACK**；不可把 WS 收到包或 Redis Pub/Sub 发布成功等同于写入成功。

- **建议顺序：**鉴权与内容校验 → PostgreSQL 事务提交（同一更新 ID 可幂等重试）→ 持久化 ACK → 本进程 WebSocket 分发及专用 Redis 协同频道跨进程转发。保证已确认的更新可恢复；客户端在未收到持久化 ACK 前应保留更新并支持重传。

- **优化边界：**允许短时间微批量合并数据库写入以降低 IO，但每份更新的持久化 ACK 必须等到所在批次真正提交。不能仅因为客户端关掉页面或 Worker 异常就丢掉已经确认的内容。

- **读取与恢复：**定期生成 Yjs 状态检查点，结合后续更新日志重建最新草稿；断线重连对比 State Vector 补齐差异。正式发布的整篇文章 Revision 与协同更新日志独立存储，不对每次键入创建正式修订。日志压缩、检查点周期和日志保留策略在数据库与协同协议阶段单独确定。

- **Q65 协同草稿数量：**同一语言的单篇内容默认只有一个共享工作草稿，多位编辑者实时协作。提交审核时冻结出独立、不可变的 Revision；即使该修订仍在等待审核，编辑者仍可继续修改共享草稿，不能改变已经提交审核的修订。首版不默认提供 Git 式多个平行草稿分支。

- 文章默认支持短代码，可内嵌在 Markdown 或 HTML 块的正文字符串中；插件代码未来可注册额外的可信块类型，渲染组件和内容 Schema 必须由可信代码声明并验证，不能向浏览器直接下发任意可执行组件。

前端文章 API 内容结构示例（允许多个不同类型块，字段名以最终 Schema 为准）：

```json
{
  "id": 123,
  "type": "article",
  "content": [
    {
      "id": "block-1",
      "type": "markdown",
      "content": "# 标题\n\nMarkdown 正文"
    },
    {
      "id": "block-2",
      "type": "html",
      "content": "<div>自定义 HTML</div>"
    }
  ]
}
```

同一内容的各语言版本作为彼此独立的 `article` / `page` 记录，分别拥有自己的 ID、内容、修订历史、审核与发布状态。版本间通过翻译关联组建立关系；关系表及外键等细节在数据库设计阶段确定。

- **Q50 未发布内容预览：**草稿、待审核等尚未公开发布的正文不进入 Next.js 公开磁盘缓存、Cloudflare 缓存或公开索引。浏览器持有效身份直接向 FastAPI 受保护接口获取预览数据，由可信 Next.js 主题组件渲染；相关响应使用不存储缓存策略，预览操作仍按内容权限检查。

- **Q59 已发布内容的协同修改：**已发布的公开修订保持稳定。多人协同编辑的是后续草稿或待审核修订，不实时覆盖已经发布的正文；经过所需审核与发布操作后，才将新修订激活并通知刷新公开缓存。

- **Q54 发布与访问策略：**发布流程状态（草稿、待审核、已发布、已撤回等）和资源访问策略分别建模，不合并到单个状态枚举。内容能否公开索引、进入 Next.js/CDN 缓存或需要登录/密码验证，必须由访问策略与发布状态共同决定；访问策略类型允许后端模块按规则扩展。首版访问策略范围见 Q60。

- **Q60 首版访问策略：**支持公开、链接可访问但不列入列表/索引、登录用户可访问、密码访问四种基本策略；后续允许模块扩展。仅适合公开分发的内容可以进入共享页面缓存；需要身份或密码验证的正文不能进入对游客公开的 Next.js/CDN 缓存。媒体本身首版仍按此前约定为公开静态资源，访问策略不会自动赋予文件保密能力。

# URL 与多语言内容

内容 URL 可自定义，不由 `article` 或 `page` 类型强制锁定命名空间。

- 编辑时默认根据标题生成路径，也允许用户手动输入。

- 默认添加语言前缀。

- 如果原文路径主体是 `test.html`，切换到英文编辑时默认建议 `/en/test.html`，允许手改。

- `.html` 是支持的路径示例，不是所有页面的强制后缀。

- 标题后续变化不应在未告知用户的情况下反复覆盖手动填写的 URL。

- **Q67 URL 生效时机：**草稿中修改的期望 URL 不立即改变既有公开路由；审核并正式发布相应 Revision 时才激活新路径，旧路径按 Q80 失效、不维护别名或自动重定向。草稿预览通过内容 ID 和具备权限的草稿/修订接口实现，不提前占用公开页面 URL。

- **Q80 旧 URL 不维护：**文章/页面正式发布到新 URL 后，旧地址直接失效；核心**不自动或默认建立历史别名、301/308 重定向，也不维护旧地址映射表**。变更路径的管理界面须提示旧外链会失效。此决定不影响 Q49：WordPress 首次迁移应尽可能直接保留原 URL；不能保留时输出差异清单，由管理员主动修改目标 URL，不由系统维护兼容跳转。

- 不存在的语言版本不生成虚假的翻译页面；访问对应地址时跳转到可用原文。

- 创建编辑草稿不等于公开该语言版本。

- 网站界面语言与正文语言是两个概念，界面翻译不要求每篇文章都有翻译。

每个语言版本都有独立且稳定的内容 ID，标题、路径、语言、正文、SEO 信息、审核与发布修订均可以独立维护；一个关联组（如 `translation_group_id`）标识这些记录互为翻译，关联组不替代各自内容 ID。原文修订后不自动覆盖、撤回或发布其他语言版本；可提示译文需要检查。公开语言切换与 SEO 替代链接只列出实际已发布版本。

- **Q57 SEO 元信息：**由核心维护统一且可由后端配置、按内容覆盖的 SEO 数据模型，至少考虑标题与摘要、Canonical URL、已发布语言版本的 `hreflang`、Sitemap、Open Graph 及 robots 索引策略。Next.js 以可信主题/页面代码及经授权的后端 SEO 元数据生成最终页面标签；具体字段与全局默认值的覆盖优先级在 API/数据模型阶段确定。

语言前缀和语言代码的映射、自动 slug 生成规则、重名处理和保留路由需要统一校验。示例中的 `zh-CN` 与 `/zh/` 不代表已经选定所有语言代码或首发语言清单。

- **Q47 路由冲突：**Next.js 注册的代码路由始终优先于数据库中的文章/页面路径。CMS 新建或修改 URL 时若已被代码路由占用，应提示冲突并阻止发布到该地址；若后续部署新增代码路由占用了现有内容 URL，代码路由仍取得访问优先级，原文章/页面数据与配置不被自动改写或删除。系统在后台标记并列出冲突，管理员自行查找、处理及修改 URL；部署流程应支持冲突预检和相应公开缓存更新。

前端页面语言以明确的 URL 为依据。localStorage 和浏览器默认语言可用于保存偏好或初次选择，不应覆盖用户显式打开的语言 URL。

- **Q35 界面语言与手动选择：**公开页面的服务端渲染以实际 URL 语言为准，保持同一公开 URL 的缓存结果稳定。用户手动选择语言时持久化偏好；后续导航优先使用真实已发布的对应语言 URL，没有译文则仍回退原文且避免重定向循环。对浏览器直接请求 FastAPI 的业务 API，统一请求客户端携带明确的语言偏好头（示例名 `X-Site-Locale`，最终名字待协议冻结），后端优先参考该头，其次为当前路由语言、`Accept-Language`、站点默认语言。普通浏览器页面导航不能假定可由站点添加自定义请求头，因此 Next.js 页面偏好用 Cookie 等浏览器可在导航时携带的机制保存；语言偏好不是身份或权限凭证。

# 前后端字符串与 API 响应

前后端分别维护各自的翻译文件。

- 前端管理主题、组件和界面字符串。

- 后端根据请求中的语言信息选择自己的翻译内容。

- 后端 JSON 翻译支持命名占位符和格式化。

- 提供专用格式化工具，自动从请求上下文取得语言，不要求每次调用都手动传 Request。

- 业务参数仍应显式传入或来自明确允许的上下文，不能把整个请求、用户对象或任意属性自动展开进模板。

- 并发请求的语言上下文必须隔离，后台任务需要明确其语言来源。

API 继续使用以下响应形状：

```json
{
  "success": true,
  "code": 200,
  "msg": "请求成功",
  "data": {}
}
```

- 保留 `JSONResponseSuccess`、`JSONResponseFail`、`JSONResponseError` 三类使用习惯。

- `data` 为 `None` 时可以省略。

- `code` 未指定时可采用 HTTP 状态码；业务码体系尚未独立冻结。

- 成功返回适当的 2xx；业务拒绝、参数或权限问题使用相应 4xx；未处理服务端错误使用 5xx，不再把所有失败都包装成 HTTP 200。

- 常规业务 JSON 使用统一外壳；文件、流和按 HTTP 规则没有响应体的响应不应被强行包裹为 JSON。

- `msg` 用于本地化展示，不作为程序判断的唯一依据。

## 翻译与邮件模板的运行时接口

- 前后端的程序翻译字符串与数据库动态内容分离。文章各语言版本具有独立内容 ID，标签及分类的本地化名称由数据库查询，不使用静态 `t()` 键模拟数据库实体。

- **后端全局翻译对象：**使用 `from app.core.i18n import i18n`，在普通路由、服务函数中直接调用同步的 `i18n.t("example.welcome", name="Pikachu")`；无需 `ctx`、`Request` 或 `await`。无请求的 Worker/Beat 可通过 `locale="en"` 显式指定。API 响应的 `code` 保持稳定，`msg` 只作本地化展示，不作为唯一业务判别依据。

- **加载顺序：**部署启动时扫描模块 `manifest` 与 `locales/`，检查命名空间和格式。FastAPI 进程先装载自己的只读全局 `i18n`，再按模块依赖顺序执行 `router_init(ctx)`；Worker/调度器若需要翻译，则分别加载所需语言包，但不为此调用 FastAPI 模块初始化入口。无需 `ctx.i18n.register()`，也不为语言包增加广播或热安装机制；前端主题与组件的语言字典由可信代码管理。

- **请求语言隔离：**FastAPI 中间件依据有效语言偏好解析 locale，以请求级 `ContextVar` 保存，结束请求时恢复；`i18n.t()` 默认读取当前请求语言。不能通过改写全局 `i18n.locale` 保存用户语言；异步后台任务应明确语言来源，不依赖已经结束的 HTTP 请求上下文。

- **Q37 缺失翻译回退：**查找请求语言字符串，缺失时可以先尝试同语言的基础代码（如 `en-US` → `en`），然后回退到网站默认语言；仍不存在则将完整翻译键作为结果并记录 `missing_translation` 警告，不因此抛出 HTTP 500。插值参数必须显式提供并按安全文本规则处理。

- **Q36 修改权限与模板边界：**程序语言包原则上不可通过后台编辑；邮件主题、HTML 和纯文本正文等属于可单独编辑的 Jinja 模板，不纳入普通 `i18n.t()`。邮件渲染以 `template_key`、`locale` 和受限变量字典调用，启用 HTML 转义并限制可访问的对象与过滤器。代码模板作为基础、数据库覆盖及模板版本管理属于推荐实现，具体存储优先级仍可单独细化。

# 用户身份与权限

默认浏览器认证方式为 HttpOnly Cookie Session，由 FastAPI 管理。

- 浏览器直接请求 FastAPI 登录与获取用户状态。

- Next.js 服务端不需要判断用户是否登录；公开 SSR 不混入用户私有信息。

- 前端通过异步用户状态请求更新头像、登录按钮、编辑入口等；真正的权限检查由 FastAPI 完成。

- 后台管理、私有数据和用户操作通过浏览器请求受保护 API。

- Session 与 API Key 在业务代码中形成统一用户身份对象，具体认证方式仍可被路由或审计逻辑识别。

- 权限采用操作能力与资源范围结合。API Key 不能突破所属用户当前权限上限。

- 支持邮箱验证；第三方登录预留接口；2FA 可选、不强制；不实现邀请注册。

- **Q63 用户注册默认关闭：**首版不开放访客自行注册，也不开放注册审核申请入口；管理员可按照权限管理流程创建账号。若以后启用公开注册，仍需经过独立配置并遵循现有邮箱验证、可选 2FA 和权限约束。

发文规则：

- 普通用户默认不能发文。

- `publish_direct` 允许直接发布。

- 只有其他发文子权限时，按审核流程发布。

- 审核权限单独管理。

- 同时具备发文与审核权限的用户允许自批，不强制双人审核。

会话存 PostgreSQL 还是 Redis、会话超时、多端管理、2FA 具体方式和 Cookie 精确名称等属于后续实现配置，不视为已经全部拍板。

- **Q48 跨域与 Cookie 配置：**生产环境 API 子域名、允许浏览器访问的 `CORS_ALLOWED_ORIGINS`、会话 Cookie 的 `SESSION_COOKIE_DOMAIN` 分别配置，绝不写死为特定域名。Cookie 支持仅发给 API 主机（不设置 `Domain`）和允许父域及子域共享（显式设置父域 `Domain`）两种模式；实际使用哪一种由部署配置决定。浏览器跨源调用受保护 API 时携带凭据，FastAPI 仅对列入白名单的精确 Origin 开放凭据响应，并单独执行 CSRF 来源及令牌校验；CORS 白名单不等于 Cookie 跨子域共享，也不替代授权检查。推荐默认主机专用 Cookie，但最终生产 Cookie 域范围保留为配置选择。

跨子域名会话应使用明确的 CORS 来源、带凭据请求和 CSRF 防护。API Session Cookie 与服务间认证凭据分开；不能把服务密钥放入浏览器配置。

- **Q61 关键操作审计：**核心维护独立于普通运行日志的审计记录，覆盖权限和账号变更、文章审核/发布/撤回、媒体删除、系统设置调整、核心及插件迁移等高风险操作；记录主体、动作、目标、时间和必要的变更摘要。审计记录的保留期限、敏感字段脱敏及导出权限在日志规范中进一步定义。

# 主题与自定义页面

主题和业务解耦。主要布局、样式和展示组件位于主题子目录，业务服务不混入主题代码。

- 主题由可信 Next.js 代码维护，不通过后台上传任意可执行代码。

- 通过配置选择主题。优先考虑运行时切换已经构建的主题；若实现成本过高，可在构建前选定。

- 新增未打包的组件或主题代码需要部署相应前端产物，后端不能只靠配置让未知 JavaScript 出现在浏览器。

- 自定义页面单独目录，采用类似后端的代码注册思路。

- 自定义页面可以套用主题框架后提供正文，也可以采用独立布局，不受主题样式接管。

- 数据库负责页面元信息，代码负责渲染。

早期关于 HTML 与普通 JavaScript 的讨论，以后续明确的可信代码边界为准：HTML 内容可以保存；可执行交互逻辑必须来自受信任的前端代码，不能把数据库中的任意脚本当成普通正文执行。

# 短代码与表单式组件

短代码的显示、样式和交互主要由可信前端组件负责，不要求每个短代码都必须有后端定义。

- 文章默认支持短代码，允许嵌套。

- 后台需要短代码发现或管理列表，便于了解可用短代码。

- 支持纯前端短代码，也支持调用 FastAPI 业务接口的混合组件。

- 组件自身处理交互事件，不为此另造一个前端全局事件总线。

- FastAPI 可以提供数据、表单定义、权限和业务路由，不下发任意 JavaScript。

- 短代码语法、注册函数名字与参数 Schema 将在前端 SDK 规范中定稿。

表单式组件页面由代码定义模板，支持 HTML 展示块、textarea、input、number、switch 等主题组件。

- 简单设置可由 Pydantic/JSON Schema 等声明生成表单；复杂页面使用可信自定义组件。

- 表单可以用于后台，也可以通过短代码用于公开页面。

- 表单按自身声明决定允许游客、登录用户或特定权限主体提交。

- 表单提交采用混合存储：模块可以自行处理，也可以显式使用框架统一提交记录。

- 公共表单外壳可以缓存；用户信息、敏感默认值、CSRF Token 和私有提交记录不能进入公共缓存。

- 不默认把密码、验证码、令牌等敏感输入完整记录到通用提交表或日志。

- 离线只读节点展示可用的公开外壳，但不能误导用户认为提交已经成功。

# 评论与历史关联

评论设计已收口，后续只在实现时补必要约束。

- 支持游客评论，游客邮箱验证默认不强制，但系统保留验证能力。

- 保留 WordPress 历史评论，后续注册用户可按邮箱关联。

- 自动关联前应验证用户对邮箱的控制权；该关联不等于证明历史游客发言的真实作者。

- 关联用户不能编辑或删除导入的旧评论。

- 支持管理员调整归档状态。导入来源与不可编辑约束独立于归档状态，避免取消归档后意外开放修改。

- 数据保存回复关系，显示不做多级嵌套。所有回复仅统一缩进一级，显示“回复 @用户名”。

- 点击回复对象可以定位到原评论，必要时加载其所在分页；不可见内容不能借定位接口泄露。

- 所有评论全局按发布时间从最早到最新排列，不按讨论串分组。时间相同可按 ID 稳定排序。

- 首屏使用公开评论快照，浏览器异步向 FastAPI 检查更新；API 暂不可用时保留已显示的快照。

- 云端保留已公开评论，离线时进入只读状态。

“允许用户切换倒序”曾被建议，但没有作为首版必做项单独确认。归档是否影响公开展示等细节属于后续状态定义，不改变旧评论不可编辑的已定原则。

# 媒体与虚拟资源引用

原始媒体内容不可变：新图片分配新媒体 ID，不覆盖旧 ID 对应的原始文件。文章历史版本因此仍可引用原文件。

- 保存原图，支持自动生成 WebP。

- 同一原图生成的 WebP 等格式是同一媒体资源的派生表示，共用媒体 ID。

- 首版不要求自动生成多种尺寸的缩略图。

- 物理文件去重、按哈希寻址与存储目录调整属于实现方案，不改变逻辑媒体 ID。

- WordPress 媒体复制到新目录，迁移时将旧引用映射到新引用；之后不因物理目录变化反复改写文章。

媒体引用使用可区别普通 HTTP 链接的自定义 URI。当前协议草案为：

```markdown
![图片说明](site://media/m_8f31a2)
```

```html
<img src="site://media/m_8f31a2" alt="图片说明">
```

虚拟 URI 只用于内容存储与编辑。Next.js 在可信的 Markdown/HTML 渲染阶段把它解析为可供浏览器直接请求的静态媒体 URL（包括 CDN 地址及需要时选择的 WebP 变体）；浏览器最终看到的是正常的 HTTP(S) 资源地址，不再依赖 FastAPI 或自定义协议解析。

- **Q55 媒体存储已确认：**默认文件保存到本地文件系统，并由 FastAPI 提供上传、预览、查看和下载等媒体管理接口；媒体 ID 与物理路径独立。未来允许增加 COS、R2 或其他对象存储桶适配器，现阶段不要求先部署云存储桶。

- **Q55 媒体解析分工已确认：**FastAPI 维护媒体 ID 与存储提供方、文件对象路径、公开域名和派生格式之间的权威映射。每次向 Next.js 提供文章、页面或其他需要媒体的公开资源数据时，同时返回本次正文所引用媒体的 URL 映射列表/对象（如 `media_urls`）。文章自身仍保存 `site://media/{id}`；Next.js 仅按照本次数据包随附的映射，在可信渲染阶段将虚拟引用替换为对应的完整 HTTP(S) URL，不自行查桶配置、猜路径或对每张图额外请求 FastAPI。映射与内容作为同一次预载/刷新数据一并缓存；媒体域名、对象路径或变体变化时，FastAPI 负责生成新映射并触发涉及页面的刷新。具体 JSON 字段名称未冻结。

文章返回数据示意（只表示语义，非冻结 API）：

```json
{
  "id": "article_123",
  "content": [
    {
      "id": "block-1",
      "type": "markdown",
      "content": "![猫](site://media/m_8f31a2)"
    }
  ],
  "media_urls": {
    "m_8f31a2": {
      "original": "https://media.example.com/2026/cat.jpg",
      "webp": "https://media.example.com/2026/cat.webp"
    }
  }
}
```

这里仅由 FastAPI 查询并组装 URL；Next.js 只处理正文节点的引用替换。完整页面缓存更新时应一起替换 `media_urls`，保证文章内容与所用媒体地址属于同一资源快照。

转换必须面向 Markdown/HTML 的资源节点与属性，不能全局替换正文或代码块中的文本。普通外部链接保留其原义。

`site://` 是当前命名草案，不是已发布的外部标准；上一轮提出的 `site://page/{id}`、分类和标签引用是合理扩展草案，尚未锁定完整语法。导出普通 Markdown/HTML 时应能把内部 URI 转换成可用链接。

媒体默认作为公开静态资源，通过 CDN 分发；首版不为媒体建立按用户或文章区分的访问权限。公开媒体的文件及资源映射应随公开快照同步，不能依赖家庭 FastAPI 在线。注意：即使某张图片仅在草稿或私有文章中被引用，其 CDN 直链也可能被任何人访问；不得把需要保密的文件放入这一媒体目录。若未来有私有附件，应另行设计受保护的存储与下载机制。

# 搜索文档

- **Q82 搜索架构已确认 A：**首版直接基于 PostgreSQL 实现站内检索，使用独立、可重建的搜索文档表与对应索引；不强制部署额外搜索引擎。搜索服务接口保留实现抽象，后续可以新增专业检索组件而不改变文章主数据结构。

至少覆盖：

- 标题。

- 摘要。

- Markdown、HTML 等内容提取出的正文纯文本。

- 分类 ID 与分类名称。

- 标签 ID 与标签名称。

- 内容 ID、语言、索引对应修订及可见性等必要信息。

分类和标签拥有稳定的唯一 ID，名称可翻译或修改。重复使用“成长”等同一标签时应复用实体，不为每篇文章重复创建。检索支持通过分类、标签反查内容。

- **Q68 分类标签修订：**每份正式内容修订保留当时关联的分类和标签稳定 ID；历史版本能够还原其分类/标签关联，但分类标签自身的本地化显示名称仍由独立实体管理。当前分类/标签的变更不能直接覆盖过去修订所记录的关联集合。

搜索文档是可重建的派生数据。正文、摘要、分类、标签或它们的名称变化，都需要更新相关索引。具体中文分词、多语言搜索权重、全文/模糊匹配及排序实现属于 PostgreSQL 搜索方案的待定技术细节，需通过真实中文/英文内容验证。

公开搜索不能泄露草稿或私有内容，包括标题、摘要、数量和高亮片段。云端精简公开搜索索引是当前离线搜索方案；它不能替代主站权限搜索或完整数据库备份。

- **Q52 多语言搜索：**默认优先在当前界面语言范围内检索并展示相关结果，提供显式的“搜索所有语言”选项；搜索 API 可接受合法语言筛选参数。不同语言文章仍为独立内容 ID，跨语言结果如何合并关联译文及排序权重可在检索契约阶段细化。

# 缓存控制与版本

FastAPI 对已配置的 Next.js 接收端提供三种缓存操作，实际请求投递与状态监控交给 Celery Worker；FastAPI 另向每个 Next.js 实例提供专用公开资源读取接口。

| 操作 | 语义 |
| --- | --- |
| invalidate | 使指定资源失效；不要求马上回源或完成重新渲染 |
| refresh | 由后端触发，Next.js 获取所需数据并更新缓存 |
| preload | 后端可直接提供文章等数据，Next.js 校验并写入缓存，避免重复回源 |

服务间路径与工程规范统一：Next.js 接收缓存控制使用 `/internal/cache/v1/*`，FastAPI 内部公开资源及 Manifest 读取使用 `/internal/v1/*`；公开业务 API 保持 `/v1/*`。确切端点、动作请求体和完整 Schema 继续在接口契约阶段定稿，不沿用早期 `/_internal/v1/cache` 示例。

缓存必须区分两层：

- 自己管理的磁盘数据缓存，如文章块、公开评论和资源映射。

- Next.js 的渲染结果缓存。

接收操作、写盘完成、版本激活、渲染预热完成不是同一个状态，返回结果不能混淆这些含义。

Manifest 用于区分已同步的公开快照版本。完整快照准备完毕后再切换当前版本；普通更新期间可保留上一份完整且仍允许公开的快照。

资源级更新按各资源修订比较，完整快照按 Manifest 版本或代际比较。不能用全站见过的最大版本号简单拒绝另一资源的较旧独立更新。

每个前端接收端分别记录投递确认与实际缓存版本；可以安全重试和去重，避免重复回放或乱序覆盖。云端主动校对和只读故障切换仍保留为后续阶段，不纳入本期单站点 ICP v1 的实现范围。

Next.js 持久化的文章、标签和搜索文档缓存不设置时间过期策略（无 TTL）；“永不过期”指没有时间到期自动回源或删除，不代表内容永远不更新。FastAPI 的缓存事件可通过 Worker 触发定点替换、刷新或撤回标记。未来增加云端节点时，再启用原先规划的 Manifest 主动校对与掉线恢复同步。

- **Q69 公开转受限/撤回后的 Next.js 清理：**FastAPI 更新内容访问状态并登记可靠的定向缓存清理事件，由既定 Worker 投递到各 Next.js 接收端；Next.js 收到后停止使用旧公开快照，清理对应文章磁盘数据文件和渲染缓存，不得在回源失败时继续展示旧正文，并保留不可见/删除版本标记以防较旧缓存重新激活。相关路由、搜索与列表缓存也应更新。Cloudflare 的自动缓存清理留给后续插件，由相应变更事件/任务触发；核心变更通过可靠事件/任务触发一次插件业务处理，Cloudflare 插件的实际清理操作使用 Celery，不交由 FastAPI 跨进程广播处理。清理通知到达之前、节点断网或 CDN 已有旧副本时，不能保证外部缓存即时全部消失，后台需区分主库已提交与节点已确认。

# 内部通信协议 ICP v1

本期仅实现单站点的 FastAPI 与一个或多个 Next.js 实例之间的通信，不纳入云端主动校对。浏览器的业务 API 与服务间内部接口独立：浏览器直接请求 FastAPI，Next.js 正常渲染优先使用自己的磁盘公开资源缓存。

## 定向投递和可靠性

- FastAPI / Worker 从部署配置 `frontends` 按稳定节点 ID 读取目标的 `base_url`、`enabled` 与 `fastapi_to_nextjs_token_env`，以有限并发向启用节点定向投递；节点记录与投递回执均关联同一 ID，不维护另一份独立可编辑的地址清单。每个 Next.js 的服务端数据源默认由 `BACKEND_BASE_URL` 装配，必要时采用明确的内部连接覆盖项。节点配置仅由管理员维护，不允许普通用户提供任意回调地址；配置顺序和域名都不作为节点身份。

- 文章等业务事务提交时，将需要同步的变更记录到 PostgreSQL 待投递事件中；Celery Worker 通过普通任务队列处理，不把任务发送扩展成广播总线。

- 事件使用稳定的 `event_id`、资源 ID 和 `revision`；每个接收端保留自己的 `pending`、`running`、`applied`、`failed`、重试次数和错误记录。可接收事件不等于缓存落盘、版本激活或 HTML 预热成功。

- 请求重试使用 `(event_id, frontend_id)` 等幂等标识，旧版本不可覆盖新版本；普通发布不阻塞等待全部节点，紧急撤回需要暴露未确认的接收端。

## 内部请求双重校验与权限

- **接收方分别配置两类校验材料：**FastAPI 的实际套接字对端 IP/CIDR 允许列表位于后端 `internal_auth.allowed_peer_ips`，Next.js 的允许列表位于前端 `backend.allowed_peer_ips`。后端从 `frontends.<node_id>.nextjs_to_fastapi_token_env` 取得校验 Next.js → FastAPI 的 Token，并据认证凭据确定节点身份；前端发送时使用 `backend.nextjs_to_fastapi_token_env`。后端调用 Next.js 时使用 `frontends.<node_id>.fastapi_to_nextjs_token_env`，前端通过 `backend.fastapi_to_nextjs_token_env` 校验该方向请求。同一调用方向的发送/接收端实际 Token 值必须一致，不同方向和节点使用独立值；IP 与 Token 的 AND 校验及最小权限检查不变。

- **必须同时通过 IP 与 Token 校验。**实际对端 IP 命中允许列表且接收方认可的 Token 匹配后，仍按认证出的服务身份检查 `cache:write`、`cache:read`、`resource:read`、`manifest:read` 等最小权限。Token 通过 `Authorization: Bearer ...` 请求头携带，不拼入 URL；服务身份由匹配的凭据确定，不信任请求体自报的节点 ID。应用层对来源/权限不符返回 HTTP 403，对缺失或错误 Token 返回 HTTP 401。

- 内部接口仍须在公网入口被阻断，并通过私有网络/受保护的 TLS 连接访问。Token 从受控环境或仅服务端密钥配置读取，不进入浏览器代码、公开运行时配置、URL 或日志；支持凭据轮换。IP 白名单和 Token 都不替代网络隔离、事件幂等及资源版本检查。

- **实际 IP 的含义：**校验来自网络连接的原始 socket peer IP，不采用 `X-Forwarded-For`、`X-Real-IP`、`Forwarded` 或 Cloudflare 转发头作为该事实，也不能使用已被代理头中间件改写的客户端 IP。经过反向代理时，应用 socket 对端是代理；若要限制原始发送端，IP 规则应在直接接收该发送端连接的可信入口执行，并阻断绕过入口直连应用的路径，应用仍校验 Token。

- **来源与目标配置独立：**白名单填写接收入口实际观察到的来源 IP，可能是 Next.js、Celery Worker 的实际出口或受控代理 IP，不由 `BACKEND_BASE_URL` 或 `frontends.<node_id>.base_url` 的域名自动解析生成。前端缓存通知通常由 Worker 发出，不能只允许 FastAPI 主机而漏掉 Worker。

- **失败时拒绝：**空允许列表不放行，无法取得可信原始对端 IP 时不降级成只查 Token；启用内部接口前必须具备可工作的双重校验入口。无效 IP/CIDR、缺少所引用的密钥或示例占位密钥应使内部服务配置校验失败。前端配置文件仅在 Next.js 服务端加载，模板纳入版本控制，实际配置及密钥忽略提交。

## 受影响 URL 反向索引

- Next.js 必须维护资源 ID → 可能受影响 URL 的反向查询能力，覆盖当前正式地址、首页及分类/标签列表等依赖页面。按 Q80 不维护历史重定向路径；某次改址事件可携带变更前 URL，仅用于清理该地址已有缓存，不建立持久旧地址映射。

- 基础主题页面由框架登记依赖；可信自定义组件可自行登记，不能假定能够自动发现所有引用。因此查询结果区分直接 URL 与间接依赖，并标明覆盖是否完整。

- 缓存事件产生时保留更新前和更新后的 URL 并集；提供按文章 ID 查询和按事件 ID 查询受影响 URL 的内部能力。返回完整的公开 URL，使用配置的站点 Origin，不写死域名。

## Cloudflare 集成边界

- CDN 暂时采用 Cloudflare 的既有回源方式。本期不内建自动清理插件，不向 Next.js 分发 Cloudflare API Token。

- 未来后端插件可在前端缓存确认后，查询文章或事件对应的 URL 集合，执行 Cloudflare 按 URL 清理；单次改址事件的旧 URL 和新 URL 都可能需要清理，但这不意味着维护历史别名或重定向。插件失败独立记录和重试。

- URL 反查是最佳努力能力，特殊自定义页面的依赖可由组件登记；不能将返回列表宣称为绝对完整。

# 云端只读与撤回

家庭服务器为业务事实来源。云端在主服务不可用时继续提供已同步的公开页面、资源和评论，进入只读模式。

- 不进行离线写入后自动合并，不把云端临时变成第二个可写主库。

- 不把用户、草稿、私有正文、私有表单默认值或会话凭据放入公开快照。

- 主服务恢复后，云端主动核对源站 Manifest/资源版本并补齐落后的内容；源站也可以通过 callback 主动推送更新。同步仅从权威源更新云端，不用旧公开缓存反向覆盖主库。

- 缓存缺失且无法取得数据时，应区分资源确实不存在与源站暂时不可用。

- 公开只读缓存不等于数据库或网站代码备份。数据库备份、代码备份及灾难恢复由 CMS 外的独立服务负责，不纳入本项目内建功能范围。

支持两种撤回方式，默认普通撤回：

- 普通撤回：主库状态更新，并异步向各公开节点传播撤回。

- 紧急撤回：追踪各服务节点和相关缓存的确认状态，对未确认结果告警，并预留停用公开出口等人工应急措施。

一旦某节点收到撤回、删除或转私有标记，它不能在回源失败时再次展示已撤回的旧正文。撤回通过资源版本更新、删除标记或不可见标记替换旧缓存状态，连带更新页面、渲染缓存与公开搜索索引。媒体默认是独立公开的 CDN 静态资源，因此文章撤回不会自动让其引用的媒体变成私有。

网络失联时无法保证远端立即得知撤回，外部下载或第三方缓存也不能保证收回。后台应明确显示“主库已撤回”与“全部公开节点已确认”的区别。

# WordPress 迁移

- 迁移全部文章和普通页面。

- 保留原有内容格式与有效 HTML，不要求把所有旧文强制转换为 Markdown。

- 保留需要的分类、标签、发布时间、路径关系及历史评论。

- 不迁移 WordPress 用户账号；导入内容的作者归属在迁移工具中明确映射。

- 旧评论保留来源信息，注册后的邮箱关联不赋予编辑和删除权限。

- 复制媒体至新存储目录，并将文章媒体引用改为新的虚拟资源引用。

- 主题只作为参考，由新主题实现，不复用 PHP 执行环境。

- **Q49 与 Q80 迁移路径规则：**迁移 WordPress 内容时尽可能把原 URL 直接作为新站的正式 URL 保留下来；如果存在代码路由冲突或其他原因无法原样保留，迁移工具列出差异并交由管理员手动修改新站目标 URL。核心不承担旧地址自动别名或永久重定向维护，迁移后变更 URL 的旧地址同样失效。

- WordPress 短代码、插件内容和不能可靠转换的块需要给出迁移报告；不能把未经识别的执行逻辑原样激活。

迁移先预检、确认外部备份已具备，再生成映射和差异报告，执行可重复、可核验的导入。CMS 本身不负责实现数据库或网站代码备份服务；精确字段清单、旧短代码处理表和切站步骤将在取得源数据后确定。

# 由已确认需求推导的实现约束

以下约束用于保证前述方案成立，不是新增业务功能。

| 约束 | 原因 |
| --- | --- |
| 服务间接口隔离于公网业务 API | 内部 URL 的命名不能代替网络限制和服务身份认证 |
| 公共缓存不包含用户态数据 | Next.js 公共 SSR 与云端快照会被多个访客共享 |
| 转私有或撤回后禁止旧正文缓存兜底 | 普通更新的可用性策略不能凌驾于页面访问权限变化 |
| 虚拟媒体 URI 不提供保密能力 | 渲染后是可直达 CDN 的公开资源 URL，媒体 ID 不作为授权机制 |
| 请求语言和身份使用请求级上下文 | 多个并发请求不能覆盖彼此的语言或用户 |
| 搜索与缓存为派生数据 | 可重建，不反向成为主业务事实来源 |
| 任务和同步按可重试设计 | 不能依赖一次网络调用永不失败或消息永不重复 |
| 元信息与可信前端构建版本匹配 | 不允许 Manifest 引用部署中不存在的组件代码 |
| 新媒体 ID 与历史版本对应原文件 | 不能以“格式升级”名义覆盖原始图片 |
| API 网络失败不等于未登录 | 登录态加载、401 拒绝与网络不可用需分别处理 |

具体安全库、缓存适配器、数据库迁移工具与部署命令将在技术规范中选型；不因为在讨论中出现过示例而自动视为不可更改。

# Q31～Q34 已确认决策

## Q31 多语言发布与翻译同步

不同语言版本是不同的文章或页面记录，分别拥有独立 ID、历史版本、审核流程与发布状态。它们只通过翻译关联关系互相识别，可复用通用的内容和权限代码。

原文更新不会自动改动其他语言的正文或发布状态；可以给译文显示待检查提示，但自动翻译与自动同步并非本轮要求。关联组标识与每组每语言的唯一性约束在数据库规范中落实。

## Q32 媒体权限与页面引用

媒体默认公开可见，以 CDN 静态资源方式分发；不实现媒体独立 ACL。虚拟媒体引用仅用于保存和编辑，Next.js 输出页面前会转换为真实 HTTP(S) 静态链接。

由于 CDN 链接可独立访问，私有文章也不能依靠媒体 URI 保护图片；保密资源不进入公开媒体目录。WebP 等派生格式仍对应同一原始媒体 ID。页面撤回与 CDN 已分发资源的清除不是同一操作。

## Q33 模块停用与数据保留

架构统一采用部署加载扩展代码，不支持运行时热安装、热卸载或任意代码下发。模块的启用状态与插件文件是否存在可以分别描述，但代码变更以部署或重启服务为边界。

插件被停用、移除或删除代码后，默认保留其表和全部已有数据；不提供自动删除或后台清理插件数据的功能。涉及已删除组件的页面应安全降级，避免前端渲染崩溃，并记录可排查的警告。

## Q34 完整备份与恢复目标

数据库备份与网站代码备份是独立的运维程序服务，不属于博客/CMS 的内建功能。云端站点镜像仅用于公开内容只读访问，不取代上述备份。

Next.js 持久化的文章、标签和搜索文档等公开缓存不按 TTL 自动过期；保留最近确认的公开版本，发生变更时通过 FastAPI 回调更新或以新版本、撤回标记替换。云端应主动定期请求权威源的 Manifest/版本状态，发现漏掉的回调或掉线恢复后自动补齐。源站不可达时沿用已同步版本、稍后重试；不存在通信时无法知道对方刚发生了什么变化。
