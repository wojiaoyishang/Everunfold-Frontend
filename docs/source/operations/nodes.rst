节点绑定、上报与同步
====================

首次绑定
--------

1. 为一台前端选用稳定的节点 ID。示例使用 ``web-main``。
   在后端节点清单加入同名条目，写明公开 ``base_url``、接收
   ``settings_receiver_url`` 和两个方向的令牌引用。采用独立清单时，
   在主配置启用 ``frontend_nodes_file``。
2. 取得后端当前的 ``source_epoch``。已鉴权的 ``GET /v1/admin/settings`` 可返回
   ``data.source_epoch``。也可在部署确认所用的 PostgreSQL 库执行只读查询。

   .. code-block:: sql

      SELECT source_epoch FROM site_settings WHERE id = 1;

3. 前端 ``FRONTEND_NODE_ID`` 使用同一个节点 ID。内联模式将来源写入
   ``[settings].source_epoch``，独立模式写入活动的 ``[profiles.<连接 ID>].source_epoch``。
   前端的两个服务共享配置、当前节点身份和可写的持久副本目录。
4. 配置相互访问的真实来源和对应令牌。前端、API 与 Worker 进程用到的参数见
   :doc:`configuration`，启动次序见 :doc:`deploy`。
5. 在后台「设置 → 节点状态与维护」打开当前节点，核对当前站点设置并选择
   「重新同步全部」。等待接收器确认后，再核对读者页面。

节点清单由谁维护
----------------

- 使用部署 TOML 时，两端分别维护各自文件。后端加载节点和内部绑定，
  前端选择本机要连接的后端。
- 需要在后端独立节点控制台管理运行中的清单时，在确认目标数据库后执行一次
  ``uv run --locked python -m tools.import_frontend_nodes``。此后 API 和后台进程从数据库
  读取同一份节点清单。公开地址及启停跟随受控页面上的变更。
- 需要增加或修改接收地址和令牌引用时，先停用当前条目，在部署清单与各处环境配置中调整绑定。
  然后执行 ``uv run --locked python -m tools.import_frontend_nodes --update-bindings``，
  重新加载相应进程配置，最后在节点控制台重新启用并验证同步。
- 后端 ``/_nodes`` 与前端 ``/admin/_nodes`` 有各自的独立诊断配置。
  前端在线时可通过管理员会话查看全站状态，管理本机预先登记的连接；
  后端控制台负责后端管理的节点清单。

读懂三类副本
------------

.. list-table::
   :header-rows: 1
   :widths: 28 72

   * - 类型
     - 内容
   * - 公开内容
     - 已公开的文章、页面、术语及相关投影。读者路由从当前完整版本读取。
   * - 公开设置
     - 公开站点设置、主题、启用的扩展公开项及可公开翻译。
   * - 节点策略
     - 单节点用的公开动态请求刷新、超时、重试和浏览量合并设置。

设置文件按节点和来源分别保存。内联模式的内容快照根来自
``[cache].directory``，独立连接在快照根下按 ``sources/<source_epoch>`` 分开。
同一副本的版本不可变。后端已确认的版本和接收器当前读到的磁盘版本应一致，
但两者分别记录。磁盘损坏、挂载变化或更换连接后，曾经的确认可能仍保留。

收到后台的「重新同步」反馈后，先看排队状态，再检查对端回执和磁盘。
同版本的完整重发可用于恢复丢失的副本；遇到已有文件与收到内容不一致时，
由运维检查当前来源、挂载与版本后处理。切换配置导致接收器显示
``receiver_restart_required`` 时，按新配置重启接收器后再重发。

切换后端或退役节点
------------------

切换活动连接前，确认该连接指向预期数据库，来源 UUID 与本机配置一致。
切换后确认接收器与 Next.js 读取同一个身份和存储，完成一次重新同步，
再浏览首页、主题菜单和一条新发布的内容。不同来源的版本号分别解释。

退役节点时，先停止新投递，撤销节点使用的方向凭据并关停其接收器。
观察残留任务和旧节点上报后，再将公开入口从部署中撤下。
保留节点历史用作审计，另为新设备分配独立节点 ID。
