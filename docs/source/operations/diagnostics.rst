按症状诊断
==========

浏览器无法打开站点
------------------

1. 比较网页、API 代理和进程监听地址。容器开发先运行
   ``./deploy/start-test.sh --check``，再查看 ``./deploy/container-dev.sh status``
   和 ``var/container/`` 下对应进程日志。
2. API ``/health/live`` 可访问但 ``/health/ready`` 返回 503 时，先读 ``checks``。
   ``database`` 检查连接，``redis`` 检查运行 Redis，``schema`` 检查迁移版本。
   若只有迁移不匹配，检查当前配置加载到了哪个数据库，再按本次发布流程显式迁移。
3. 通过 Next.js 直接监听地址访问 ``/health/ready``，区分 Web 进程故障与冷节点缺少有效快照。
   若节点已绑定且尚无首份公开内容，执行首次同步后再核对读者站点。

后台能加载但登录或写入失败
--------------------------

- 对照浏览器发出的 ``Origin`` 和后端允许列表，检查协议、主机和端口是否一致。
  比如 ``localhost`` 与 ``127.0.0.1`` 是不同来源。
- 检查请求实际使用的公开 API 根地址和浏览器 Cookie 保存范围。
  使用 HTTPS 的公开入口应保持 Cookie Secure。会话变化后从 API 读取新的 CSRF 值。
- 验证用户是否具备业务能力，以及页面是否属于当前账户可以操作的站点。
  保存返回 409 时读取服务器新版本，保留待合并的本地修改。
- 若只有协作失败，检查 ``/ws/v1/`` 是否到达 FastAPI、网关是否传递 Upgrade、
  协作票据是否在有效期内，以及连接能否持续。

发布后节点长期等待同步
----------------------

1. 在后台「设置 → 节点状态与维护」检查目标节点、期望版本、确认版本和磁盘版本。
   节点上报表明 Next.js 的清单上报进程可连 API；实际同步还依赖 Worker 到接收器的独立通路。
2. 核对当前节点已启用、接收器已启动、内部地址可达，并检查两个方向的令牌和实际来源 IP。
   接收器返回 403 时同时检查这两个条件。返回
   ``receiver_restart_required`` 时，用活动配置重启接收器。
3. 比较后端来源 UUID、活动前端连接和实际挂载目录。版本相同但磁盘显示缺失时，
   先确认可写的持久存储，再对目标节点进行「重新同步」。
4. 检查「运行与任务」中的 Worker、Scheduler、队列和失败记录。处理连接或存储原因后，
   再选择重发当前节点对应资源。验证读者页面已显示预期公开版本。

缓存已满或命中率异常
--------------------

- 「节点缓存」显示设置、节点策略和公开内容的磁盘版本、文件数与逻辑大小。
  「清理旧版本」只处理每次上限内的旧文件。当前版本不可用时会跳过该项。
  先确认目标节点与来源，清理后重新读取报告。清理操作不会处理外部 CDN。
- 「后端查询缓存」按时间窗口统计站点信息、分类标签和常用公开内容列表。
  命中率按命中与未命中计算，可结合绕过、错误、读库次数及耗时判断影响。
  缓存实例不可用时，验证 PostgreSQL 查询路径与监控指标。
- 若公开内容版本已更新但浏览器仍见旧值，逐层核对节点磁盘、读者请求和 CDN 的缓存规则。
  后台的节点清理不涉及 Next.js 的 ``.next``，也不刷新浏览器中已打开的页面。

邮件、AI 或后台作业等待
--------------------------

先检查 Worker 和 Scheduler 可用，确认后台已登记对应平台或插件。
查看任务和通知投递状态，再核对发信渠道或模型服务商配置。
站点维护的健康检查会检查邮件配置，实际邮件投递用隔离收件人测试。
只在确认不会重复产生外部副作用时发起重试。诊断报告使用任务 ID、时间、状态与节点，
凭据、会话令牌和正文留在部署环境。
