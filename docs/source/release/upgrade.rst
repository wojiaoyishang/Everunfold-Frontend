更新与回滚演练
==============

这页用于配合 :doc:`prerelease` 的配套提交记录。在独立环境完成至少一次从上一批版本的升级，
并保留每一步的检查结果。实例进程、网络和数据恢复的完整操作见
:doc:`../operations/deploy` 与 :doc:`../operations/recovery`。

更新前准备
----------

1. 从现有环境记录前后端提交、已安装插件版本和数据库迁移头。验证新前端的契约锁
   能从相应后端的 Git 对象恢复。
2. 备份数据库、媒体和加密数据所需主密钥。用隔离的数据库、Redis 作用域、
   媒体目录和前端节点存储恢复一份待验证环境。
3. 收集验证样例。准备旧版已发布文章、受限页面、多语言草稿及当前启用的主题和插件，
   确认升级后仍能读取预期状态。

应用新版本
----------

1. 在后端运行 ``alembic current`` 和 ``alembic heads``，核对起始迁移和目标。
   依据构建记录部署新后端，并显式应用迁移。按预发布计划再启动 API、Worker 和 Scheduler。
2. 构建并更新前端和接收器。在后台对照插件清单及节点上报，确认站点设置和内容都能同步。
3. 在公开读者页面核对旧已发布内容，验证原先受限内容仍需授权。
   创建并发布一条测试内容，等待各节点应用，再检查 RSS 与站点地图。
4. 编辑一份旧草稿，核对提交、历史和恢复。检查后台权限和已启用扩展。
   最后检查隔离实例的任务失败和投递重试。

决定是否回退
------------

若仅前端故障且已验证旧前端仍兼容当前接口，可以先回退该前端。
涉及数据库变更时，核对迁移是否支持安全降级以及升级后的数据能否保留。
例如多服务商配置可能使旧版无法表示当前数据，迁移会拒绝丢失配置的降级。
需要恢复备份时按记录选择对应的代码、数据库、媒体和主密钥，
分开验证该来源与旧节点目录，再恢复对外服务。

更新报告至少记录成功或失败的步骤、配套提交、迁移头、节点应用结果和下一次操作。
文档独立构建与发布见 :doc:`documentation`。
