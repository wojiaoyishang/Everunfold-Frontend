# 主题配置与缓存边界

更新：2026-10-31。来源：用户本轮截图反馈及“主题色切换时左侧卡片、顶部导航一起变色”的补充。本文区分已确认需求、当前实现和后续工程设计；原记录的后台未实现限制现由 [ADR 0024](../decisions/0024-versioned-settings-delivery.md) 更新：首批站点/主题表单、写 API 和设置副本可靠下发已实现，完整文章缓存通知链路仍未实现。下面配置表保留当时盘点，实际开放字段见 [操作指南](../development/settings.md)。

## 已确认的可配置区域

| 区域 | 后续后台维护内容 | 当前来源与限制 |
| --- | --- | --- |
| 站点品牌 | 名称、导航品牌文字、横幅标题/副标题、图像 | 已读取公开 Site 数据；部分个人化别名/文案由主题参考映射补齐 |
| 导航 | 一棵有稳定节点 ID 的菜单树，含名称、链接、图标、顺序、子菜单及显示开关 | 顶栏、侧栏均调用 siteNavigation；一级来自 Site.navigation，二级和图标仍有主题参考配置 |
| 侧栏个人卡片 | 头像、昵称、简介、社交链接、统计项的显示/顺序/标签 | 头像、作者、简介和统计来自 Site；部分个人文案和社交链接仍在 navigation.ts 中 |
| 主题默认值 | 主题色、显示偏好初值及允许选择的可信主题能力 | 本轮只实现访客本机偏好，没有后台默认值发布机制 |

统计数字必须派生自后端允许公开的数据；可设置展示方式，不允许填写假文章数或将私密内容计入公开统计。自定义页面正文和路由不属于菜单配置自动生成的能力。

顶栏和侧栏必须引用同一份解析后的菜单树，不能维护两套独立内容。本轮修正参考映射覆盖后端菜单名称的问题；未来正式配置上线时要移除对应参考补全。配置缺失和管理员主动配置为空要区分：空菜单或空社交链接不能重新冒出主题默认项。当前空菜单回退仅用于原型启动，不是正式管理语义。

后端发布正式版本化配置契约后，前端生成类型/客户端；本文表格是概念需求，不是第二份 DTO。仅支持可信代码中的图标/组件标识、安全链接及公开媒体映射，不接收任意 JavaScript、PHP、可执行 HTML 或用户提供的内部回调地址。

## 当前已实现的访客偏好

- 首页筛选位于右下阅读设置的“首页内容”，保存在 everunfold.home-feed.v1；选项使用生成展示契约中的 article/shuoshuo，另有界面 all。首页不再放置独立筛选栏和样例提示栏；说说卡片仍标明示例。
- 显式 URL 的 type 优先于本机偏好。设置变更在首页用软导航更新 type、清除 page；搜索和 /ss 等页面保持当前内容，只保存下次首页偏好。分页始终保留显式 type，包括 all。
- 普通首页链接在客户端导航前附加已保存的筛选；直接打开无 type 的首页，服务端先输出公共默认结果，水合后以已保存偏好替换 URL。因此首次直接访问可能短暂显示公共默认列表，不用用户 Cookie 污染共享 SSR。
- 存储被禁用时退化为本次页面会话内偏好；支持 storage 事件。首页筛选、外观、背景播放等访客设置均不写入业务数据库或公开快照。
- 主题色通过统一变量同时驱动链接、菜单高亮、顶部导航、侧栏标题渐变、侧栏卡片底色和进度条。带白字的品牌填充使用经过对比度处理的深色调；深色模式的链接可用浅色调，品牌填充不随之漂白。仍沿用原外观偏好的持久化和首屏初始化。

## 后续配置保存与缓存设计（未实现）

1. **写入事实源**：授权的后台修改通过 FastAPI 用例写 PostgreSQL；配置、审计和可靠事件在同一事务提交。Redis 和 Next.js 缓存不是配置主库。具体表、字段和公开契约升级由后端单独设计。
2. **资源版本**：公开配置作为版本化资源发布，沿用 source_epoch、稳定资源 ID、revision 与 event_id 的基线。菜单、品牌、侧栏同一批配置作为一致版本应用；公开快照 generation 指向完整已激活数据，不能在同代快照中混入多个配置版本。
3. **影响范围**：变更必须覆盖首页、文章/说说/归档等公共壳，顶栏/侧栏/移动菜单及相关元信息；同时考虑公开数据缓存、框架派生缓存、浏览器预取和已挂载公共壳。只刷新首页 HTML 会造成不同路由和菜单区域版本错位。
4. **交付与落盘**：由既定 Worker 向已配置节点通知，校验真实 socket 来源 IP AND Token 和最小权限；处理重复、乱序、旧 epoch、失败重试及恢复。接收成功不等于落盘/激活成功。配置和依赖媒体映射校验后原子替换，记录激活版本，重启读取最后完整可用公开版本。
5. **无时间 TTL**：普通配置刷新失败可以保留仍允许公开的完整旧版本；不能靠固定过期时间或删除 .next 文件保持一致。已知撤回/转受限的内容必须遵守不可见标记和禁止旧正文回退的基线，不能借“菜单缓存”绕过。
6. **客户端一致应用**：后续正式同步机制必须让常驻 BlogShell 的顶栏、侧栏和移动菜单一同接收新配置。不能用一次初始化 state 永久冻结菜单，也不能在每个组件各自拉取不同版本。跨标签传播和已打开页面何时检查版本须在实现时明确并验证，不假设当前路由切换已提供后台配置同步。
7. **个性偏好隔离**：公开默认设置与浏览器覆盖值分别管理，管理员改主题默认值不覆盖访客已选偏好。公开列表缓存以规范化路径、type/page/query 和数据版本区分；不能把带访客偏好的结果写回默认首页缓存。

## 正式配置上线前的验收门槛

上述链路须落实基线对应 P0 和真实多进程验收，至少覆盖：保存事务失败无半成品；新旧事件乱序/重复；进程重启后保留配置；配置为空不复活默认项；所有菜单区域/路由同步更新；预取后导航不倒退；节点离线恢复；媒体变更；撤回内容不回退；访客设置不进入共享快照。当前 cache_receiver=false，不能以本轮外观切换或构建通过代替这些验收。
