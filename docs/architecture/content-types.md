# 内容类型注册与公开展示衔接

更新：2026-11-02，content-types-5。**文章/说说注册、独立编辑页、发布/撤回及完整快照同步已实现；历史说说导入仍未执行。** 本期见 [ADR 0031](../decisions/0031-content-publication-and-editor-pages.md) 与 [管理指南](../development/content-management.md)。

## 当前后台实现

文章和说说是后端可信注册的独立类型，前端从 content-admin 1.4.0 契约生成类型描述与操作，再注册编译内编辑器。各自有独立列表与编辑页，复用创建、版本校验、编辑、搜索分页、回收恢复及发布用例；代码页面目录单独管理。

工作草稿、完整历史和幂等回执在 PostgreSQL；保存草稿与发布明确分开。发布将同一稳定 ID 投影到 contents，同事务产生不可变 release 与可靠事件。公开 kind 新增 shuoshuo，唯一前端适配层转换为展示 type。四条硬编码说说已移除，前台仅使用后端公开投影；显式 seed 的内容也必须发布后才显示。已完成 Markdown/HTML 多块基本编辑、媒体/封面、分类标签、评论/SEO 设置与正式发布投影；Y.Doc 和完整富文本仍未完成。默认根级标题链接、分类父级、密码与定时开放见 ADR 0034；受限正文不进入公开快照，POST reader/access 仅返回当前页面内存。public0.4兼容0.1/0.2/0.3，presentation仍为独立展示模型；未接通的展示草案字段不能当正式业务能力。

以下保留此前前台阶段依据，涉及“本轮”均指 2026-10-31 前台阶段。

## 历史前台阶段（2026-10-31）

后端提交 `29f198a` 发布 `contracts/presentation-v0.2.schema.json`（0.2.0-preview.1），源模型为 `app/modules/content/presentation_schema.py`。前端通过 contract:sync 生成 `presentation-contract.ts`、Schema 副本与来源 SHA256；旧 0.1 kind 在唯一适配层转为展示 type。首页混排、/ss 说说列表、轻量详情、搜索类型、长文折叠和共享阅读能力已实现。四条虚构说说不写入数据库/快照、不计入真实统计；评论/喜欢仅演示。详见 ADR 0007 和 frontend-reader-verification.md。

草案字段 type=article/shuoshuo/page，含 comments_open、reaction_count、access、opens_at；只允许说说无标题。受限投影禁止正文、摘要、媒体映射，定时状态必须给开放时间。这不是密码验证/开放倒计时/评论审核 API 已接通的证明，前台当前只消费公开记录。

## 已确认需求

- 文章与说说是不同的内容类型，首页呈现有差异。后台设计与文章类型设计时必须统一顶层 type，前后端使用同一份后端权威定义。
- 说说不能仅根据“没有标题”“摘要很短”“属于某分类”推断，也不能被当作 Markdown/HTML 正文块类型。
- 原首页中的文章卡片当前可整卡点击；后续说说卡片包含正文链接、图片及互动控件时，应保留这些元素的独立交互，不能机械覆盖全部正文。

## 现状与原站依据

历史公开契约 0.1.0 只有 kind=article/page；本轮 public 快照 0.2.0 增加 shuoshuo，保留 kind 字段及旧 0.1 读取兼容。presentation-v0.2 是独立展示草案，不能把两个 0.2 版本视作同一份业务契约。

原 Argon 的 functions.php 用 register_post_type('shuoshuo') 注册独立类型，首页配置可查询 post + shuoshuo。template-parts/content-shuoshuo.php 和 content-shuoshuo-preview.php 展示可选标题、正文、日期/时间和互动摘要；文章则使用封面、标题、摘要及阅读全文。它们说明类型和展示应分开建模，不代表新系统必须复制其全部行为。

## 展示语义（草案已实现，生产迁移待定）

| 语义 | 建议稳定值 | 首页展示建议 |
| --- | --- | --- |
| 长文章 | article | 封面/标题、摘要、分类标签、阅读信息、整卡进入详情 |
| 说说 | shuoshuo | 轻量动态卡片，日期和正文优先，标题可选，允许图片及互动摘要；是否折叠长正文另定 |
| 普通页面 | page | 共用内容生命周期和正文能力，通常不混入首页时间流 |

顶层 content.type 表示内容种类；body[].type 表示块格式/块能力，二者作用域不同。发布状态、访问策略、语言、置顶和编辑权限仍是各自字段，不混入 type 枚举。共享 ID/URL/作者/时间/正文/媒体映射及发布流程，类型差异集中在验证与渲染分支，不复制整套内容服务。

## 实施顺序与交接检查点

1. 先只读盘点备份中的实际 shuoshuo、状态、原路径、媒体和评论关系，输出数量及未迁移差异；现有“78 文章、9 页面”的试导入统计不能当作包含说说。
2. 后端决定正式 type 枚举、可选标题/封面规则和未知类型处理，明确 kind → type 的契约版本与兼容窗口；数据库迁移和历史数据映射显式执行，不由启动自动改库。
3. 同步导入器、查询过滤、归档/搜索/统计、OpenAPI/JSON Schema、公开快照版本，再生成前端类型。新旧快照的兼容、回滚和撤回规则必须同时验证，不能只手改生成代码。
4. 后台编辑器按类型提供合适字段，前台用单一渲染入口分发 ArticleCard/ShuoshuoCard 并共享元信息、媒体、时间与互动组件。实际组件名在实施时确定，当前不创建占位框架。
5. 验证原 URL、稳定 ID、公开访问边界、分页排序、历史评论关系和媒体引用；用户验收两种首页展示。点赞、评论发布和通知须使用正式业务接口，不延用本页演示状态。
